## 1. Как устроено веб-приложение. Razor Pages vs MVC vs Web API

**Что это.** Любой запрос проходит путь: браузер (клиент) → сервер → код приложения →
ответ обратно клиенту. ASP.NET Core даёт три подхода организовать этот код, и все три мы
потрогали:

- **Razor Pages** (проект Notes): страница и её логика лежат рядом. Браузер запрашивает
  страницу → отрабатывает обработчик `OnGet`/`OnPost` в `PageModel` → формируется HTML →
  уходит клиенту. Удобно, когда приложение «страничное».
- **MVC** (проект PersonalAccount): запрос принимает **Controller**, выбирает действие,
  готовит **Model** (данные) и отдаёт их во **View**, которая рендерит HTML. Один
  контроллер обслуживает много представлений. Подходит, когда логики больше.
- **Web API** (проект Marketplace): контроллер возвращает не HTML, а **данные в JSON**.
  HTML рисует уже отдельный фронтенд. Так бэкенд и фронтенд развязаны и могут жить
  отдельно.

**Почему важно.** Это три ответа на один вопрос «кто и как формирует ответ клиенту».
Razor Pages и MVC отдают готовый HTML (рендер на сервере), Web API отдаёт данные, а
рендер уходит на клиент. Выбор зависит от задачи: простой сайт, сайт посложнее или
бэкенд для отдельного фронта/мобилки.

**О чём поговорить.** Пусть студент на примере наших проектов объяснит, чем отличается
ответ Razor Pages/MVC от ответа Web API (HTML против JSON) и почему для Marketplace
выбрали именно API + отдельный фронт.

## 2. Dependency Injection и принципы проектирования

**Что это.** Класс не создаёт свои зависимости сам (`new SomeService()`), а получает их
готовыми — обычно через конструктор. За создание и подстановку отвечает **IoC-контейнер**,
встроенный в ASP.NET Core. Мы регистрировали зависимости в `Program.cs`:
`builder.Services.AddScoped<INoteService, SqliteNoteService>()`.

**Почему так.** Две причины:
- **Работа через интерфейс** (буква **D** в SOLID — инверсия зависимостей). `IndexModel`
  зависит от `INoteService`, а не от конкретного класса. Поэтому реализацию можно
  подменить, не трогая того, кто её использует: в Notes мы переключались между
  `InMemoryNoteService` и `SqliteNoteService` одной строчкой.
- **Меньше связанность, проще тестировать и менять.** Контейнер сам собирает граф
  зависимостей и передаёт их в конструкторы.

**Жизненные циклы** (важная подтема):
- **Singleton** — один объект на всё приложение. `InMemoryNoteService` был синглтоном:
  он хранит список заметок внутри себя, значит должен жить всё время.
- **Scoped** — один объект на HTTP-запрос. `SqliteNoteService` — scoped, потому что
  завязан на `DbContext`, который тоже scoped.
- **Transient** — новый каждый раз.

**О чём поговорить.** «Почему `IndexModel` работает через `INoteService`, а не напрямую с
классом?» и «почему in-memory сервис был Singleton, а sqlite — Scoped?». Если поймал идею
подмены реализации и срок жизни — тема понята.

## 3. Слои приложения и модели данных

**Что это.** Код разнесён по слоям, у каждого своя ответственность:
**Controller → Service → Repository → DbContext/БД.**
- **Controller** — тонкий: принял запрос, позвал сервис, вернул ответ.
- **Service** — бизнес-логика (например, в Marketplace логика покупки).
- **Repository** — доступ к данным (запросы к базе).

Параллельно одни и те же данные описываются **разными классами**:
- **Entity** — как строка лежит в БД (`ProductEntity`).
- **Model** — доменная модель в коде (`ProductModel`).
- **ViewModel / DTO** — что отдаём или принимаем наружу. В API это **Request**/**Response**
  (`CreateProductRequest`, `GetProductPreviewResponse`).

Перекладывание между ними делает **маппер** (`ProductMapper`).

**Почему так.** Разделение ответственности. Если свалить всё в контроллер — он
превращается в «кашу» (про это прямым текстом в ДЗ №5). Разные модели нужны, потому что
формат хранения в БД, формат внутренней логики и формат, который видит клиент, — это
**разные вещи** и меняются независимо. Например, в кабинете администратора мы намеренно
завели отдельный `AdminCabinetStudentViewModel`, хотя поля поначалу совпадали с профилем
студента: у них разная ответственность.

**О чём поговорить.** «Зачем нам и Entity, и Model, и ViewModel — почему не один класс
на всё?» Хороший ответ — про разделение ответственности и независимость изменений.

## 4. Базы данных через EF Core

**Что это.** EF Core — ORM: работаем с базой как с обычными C#-объектами.
- **DbContext** — точка входа к базе; `DbSet<T>` — таблица.
- **Миграции** — версионируют схему БД под изменения в коде:
  `dotnet ef migrations add Name`, `dotnet ef database update`.
- **SaveChanges** — фактически отправляет накопленные изменения в базу. До него
  `Add`/`Remove`/`Update` только копят изменения в контексте.

**Почему так.**
- Миграции дают воспроизводимую и версионируемую схему: не правим базу руками, а
  описываем изменение в коде. В Marketplace миграции вообще вынесли в отдельный контейнер,
  чтобы накатить схему один раз до старта сервисов.
- `SaveChanges` отправляет всё разом (одна транзакция) — это и эффективнее, и безопаснее.
- **Фильтровать лучше запросом в базу, а не в памяти.** В `SqliteNoteService` фильтр
  строили через `IQueryable` + `Where`, и условие уезжало в SQL — из базы приходили только
  нужные строки. Если бы тянули всё и фильтровали в памяти (`List.Where`), грузили бы
  лишнее. Для режима «все заметки» лишний `Where` не добавляли вовсе.

**Полезные детали для разговора:** `enum` по умолчанию хранится числом (`Admin → 0`,
`Student → 1`) — это всплывало, когда вручную добавляли студентов в SQLite. `AsNoTracking`
для запросов только на чтение.

**О чём поговорить.** «Что делает SaveChanges и почему Add без него ничего не меняет в
базе?» и «почему в Sqlite-сервисе мы фильтровали запросом, а не в памяти?».

## 5. Формы и обработка запросов (GET/POST, model binding, PRG)

**Что это.** Браузер общается с сервером запросами. Для нас ключевая пара:
- **GET** — получить/показать данные, ничего не меняет на сервере. Фильтр заметок делали
  через GET: значение уходит в URL, страницу можно обновить и расшарить.
- **POST** — изменить данные на сервере. Удаление заметки, редактирование профиля,
  подтверждение почты — всё POST.

**Model binding** — как данные формы попадают в параметры метода: атрибут `name` у
`<input>`/`<select>` связывается с именем параметра. Скрытое поле
`<input type="hidden" name="id">` так передавало id нужной заметки.

**Паттерн PRG (Post-Redirect-Get).** После POST мы не возвращаем HTML сразу, а делаем
`RedirectToPage()` / `RedirectToAction()`. Тогда браузер заново запрашивает страницу
(GET). Иначе при нажатии F5 форма отправилась бы повторно (повторное удаление/создание).

**Почему так.** GET и POST разделяют «чтение» и «изменение» — это и про корректность
(GET-запрос можно безопасно повторять), и про удобство (фильтр в URL). PRG спасает от
двойной отправки.

**О чём поговорить.** «Почему фильтрацию сделали через GET, а удаление через POST?» и
«зачем после удаления делаем Redirect, а не возвращаем страницу сразу?».

## 6. Валидация данных

**Что это.** Проверка того, что прислал пользователь. В форме редактирования профиля
правила задавали атрибутами на **ViewModel** (`[Required]`), а в контроллере проверяли
`ModelState.IsValid`. Невалидную форму не пропускали, ошибки показывали на странице.

**Почему так.**
- **Клиенту нельзя доверять.** Проверки в браузере (JS) легко обойти — отправить запрос
  мимо формы. Поэтому серверная проверка обязательна. В ДЗ №4 мы специально **дублировали**
  проверку «новый пароль ≠ старый» на сервере, даже если она уже была на клиенте.
- **ViewModel с правилами** держит валидацию рядом с данными формы и отделяет «то, что
  пришло из формы» от доменной модели.

**CSRF и antiforgery.** Атрибут `[ValidateAntiForgeryToken]` защищает POST-формы от
подделки межсайтовых запросов: чужой сайт не сможет отправить валидную форму от имени
залогиненного пользователя, потому что у него нет одноразового токена.

**О чём поговорить.** «Почему проверки на клиенте недостаточно?» — ответ про то, что
клиент можно обойти. Про antiforgery достаточно понимания идеи «защита от чужих форм».

## 7. Аутентификация и авторизация

**Что это — две разные вещи:**
- **Аутентификация** — «кто ты» (вход по логину/паролю).
- **Авторизация** — «что тебе можно» (доступ по роли/правам).

**Как работало у нас (cookie-based).**
- При входе проверяем пароль, собираем **claims** (утверждения о пользователе: Id, Email,
  Role), кладём их в **ClaimsPrincipal** и вызываем `SignInAsync` — ASP.NET выписывает
  зашифрованную cookie. На каждом следующем запросе по ней приложение понимает, кто это.
- Роли клали отдельным claim (`ClaimTypes.Role`). Доступ ограничивали атрибутом
  `[Authorize(Roles = "Admin")]` или проверкой `User.IsInRole(...)`. Так кабинет
  администратора был доступен только админам.

**Хэширование паролей.** Мы храним **не пароль, а его хэш** (`IPasswordHasher`,
`HashPassword` / `VerifyHashedPassword`). Хэш — необратимое преобразование: при входе
хэшируем введённый пароль и сравниваем с сохранённым. Если базу украдут — паролей в ней
не видно. Хранить пароль в открытом виде нельзя.

**Порядок в пайплайне.** В `Program.cs` сначала `UseAuthentication()` (определить, кто
пользователь), потом `UseAuthorization()` (проверить права). Порядок логичен: нельзя
проверить права, не зная, кто перед нами.

**О чём поговорить.** «Чем аутентификация отличается от авторизации?», «почему храним хэш,
а не пароль?», «как ограничили кабинет админа только админам?».

## 8. Конфигурация и секреты

**Что это.** Настройки приложения (строки подключения, параметры SMTP) лежат в
`appsettings.json`, читаем их через `IConfiguration` (`GetConnectionString`) или через
**Options-паттерн** (`Configure<SmtpSettings>` → внедряется как типизированная зависимость).

**Секреты — отдельно.** Пароль от Google-почты для отправки писем и логин/пароль админа
из `DbBootstrap` мы **не** клали в `appsettings.json` и **не** коммитили в Git. Для них —
**user-secrets** (`dotnet user-secrets set ...`), а в Marketplace — переменные окружения /
`.env`.

**Почему так.** Секреты в репозитории — это утечка: любой, кто получит доступ к коду,
получит и доступ к почте/аккаунтам. Поэтому секрет хранится локально на машине разработчика
и не уходит на GitHub. Отдельная иллюстрация — Google **App Password**: одноразовый
отзываемый токен, который не жалко потерять (сгенерировал, положил в секреты, при утрате
выпустил новый).

**О чём поговорить.** «Где лежат настройки и почему пароли туда не кладём?» — ответ про
то, что секреты не должны попасть в Git.

## 9. Web API и REST

**Что это.** Web API — бэкенд, который отдаёт **данные (JSON)**, а не HTML. Контроллеры
наследуют `ControllerBase` и помечены `[ApiController]`.

**REST-идеи, которые использовали в `ProductsController`:**
- **HTTP-методы под CRUD:** GET — получить, POST — создать, PUT — обновить, DELETE —
  удалить.
- **Коды ответов вместо «просто объекта»:** `Ok()` (200), `NotFound()` (404),
  `NoContent()` (204), `CreatedAtRoute()` (201). Клиент по статусу понимает результат.
- **Откуда параметры:** `[FromBody]` — из тела запроса (JSON), `[FromRoute]` — из URL
  (`{id}`).
- **Swagger / OpenAPI** — интерактивная документация и способ потыкать API руками.

**Почему так.** Разделение бэкенда и фронтенда: одно и то же API может обслуживать
веб-фронт, мобильное приложение и т.д. Стандартные методы и коды делают API предсказуемым —
не нужно гадать, что вернёт ручка.

**О чём поговорить.** «Чем API отличается от MVC-сайта?» (JSON против HTML) и «зачем
возвращать NotFound/NoContent, а не просто данные?».

## 10. Микросервисы и инфраструктура

**Что это.** Marketplace разбит на несколько отдельных сервисов: **ProductsApi**,
**UsersApi**, **PurchaseApi**, плюс общая библиотека **Shared** и контейнер **Migrations**.
Перед ними стоит **API Gateway** на nginx.

- **API Gateway (nginx)** — единая точка входа. По пути запроса (`/api/products`,
  `/api/users`, `/api/purchases`) reverse-proxy перенаправляет его в нужный сервис.
- **Docker / docker compose** — каждый сервис упакован в свой образ; `compose.yaml`
  поднимает всё вместе: gateway, три API, базу Postgres и миграции. `depends_on` задаёт
  порядок старта, тома (volumes) хранят данные базы и ключи.
- **Общая авторизация между сервисами.** Cookie, выписанная UsersApi, должна
  приниматься в ProductsApi. Для этого сервисы делят общий ключ **DataProtection** (один
  том на всех) — иначе каждый шифровал бы cookie по-своему.

**Почему так.** Разбиение на сервисы даёт независимость: каждый отвечает за свою область,
их можно развивать и разворачивать отдельно. Gateway прячет эту внутреннюю структуру за
одним адресом. Docker делает запуск воспроизводимым — «работает у меня» превращается в
«работает везде одинаково».

**Образ vs контейнер** (частый вопрос): образ — шаблон (рецепт), контейнер — запущенный из
него экземпляр.

**О чём поговорить.** «Зачем разбивать на несколько сервисов, а не делать один большой?»,
«что делает gateway?», «чем образ отличается от контейнера?». Про общий ключ DataProtection
— только для сильных.

## 11. Транзакции и конкурентный доступ

**Что это.** Операция покупки в `PurchaseService` меняет сразу несколько вещей:
списать деньги у покупателя, начислить продавцу, уменьшить остаток товара, создать запись о
покупке. Всё это обёрнуто в **транзакцию**: `BeginTransaction` → при успехе `Commit`, при
ошибке `Rollback`.

**Почему транзакция.** **Атомарность** — «всё или ничего». Без неё при сбое на середине
данные останутся неконсистентными: деньги списали, а товар не уменьшили. Транзакция
гарантирует, что применятся либо все изменения, либо ни одного.

**Конкурентный доступ и блокировка.** Два покупателя одновременно берут последний товар.
Чтобы его не продали дважды, в `FindByIdWithLockAsync` мы читаем строку с
`SELECT ... FOR UPDATE` — она блокируется до конца транзакции, второй запрос ждёт. Это
защита от **race condition** (состояния гонки).

**О чём поговорить.** «Почему покупку оборачиваем в транзакцию?» (атомарность) и «что
будет без неё, если на середине ошибка?». Про `FOR UPDATE`/гонку — для самых сильных.

## 12. Основы HTTP

**Что это.** HTTP — протокол запрос–ответ между клиентом и сервером. Понадобятся:
- **Статус-коды:** 200 OK, 201 Created, 204 No Content, 401 Unauthorized (не вошёл),
  403 Forbidden (вошёл, но нет прав), 404 Not Found, 500 — ошибка сервера.
- **Cookie** — данные, которые хранятся у клиента и шлются с каждым запросом; так держится
  состояние входа (наша авторизация).
- **JSON** — формат, в котором API обменивается данными с фронтендом.

**Почему важно.** Это «алфавит» всего веба: и авторизация (cookie + 401/403), и API
(методы + статусы + JSON) стоят на этих понятиях.

**О чём поговорить.** «Что значат 401 и 403 — в чём разница?» (не аутентифицирован против
нет прав). Хороший короткий вопрос-связка между темами.

## 13. Фронтенд и связь с API

**Что это.** Фронтенд Marketplace — на Next.js/React/TypeScript.
- **Компонент** — переиспользуемый кусок интерфейса (`ProductCard`). **Props** — входные
  данные компонента (имя товара, картинка, даты).
- **Поход в API.** Фронт берёт товары из нашего бэкенда: axios делает GET на
  `/api/products`, получает JSON и рендерит из него карточки.
- **Типы TypeScript.** Интерфейс `ProductPreview` описывает форму данных от API — это даёт
  автодополнение и ловит ошибки ещё на этапе написания кода.

**Почему так.** Компонентный подход = собираем UI из кирпичиков. Типы = меньше ошибок,
когда данные ходят между фронтом и API. Это замыкает картину «Web API отдаёт JSON →
фронтенд его рисует».

**О чём поговорить.** «Что такое компонент и props на примере карточки товара?» и «как
фронт получает список товаров?». Тема мягкая, без глубокого погружения.

## 14. Git и рабочий процесс

**Что это.** Так мы сдавали домашки:
- **Fork** — своя копия учебного репозитория, куда есть права писать.
- **origin vs upstream** — `origin` это свой форк (туда пушим домашку), `upstream` —
  учебный репозиторий (оттуда подтягиваем свежие изменения с занятий).
- **Цикл изменений:** `git add` → `git commit` → `git push`.
- **Pull Request** — предложение влить ветку с домашкой; в нём виден diff и можно
  обсудить изменения. Домашки сдавали именно ссылкой на открытый PR.

**Почему так.** Ветки изолируют работу, форк даёт право писать в свою копию, а PR — это
способ показать и обсудить изменения, не ломая основную ветку. Ровно так устроена работа в
реальных командах.

**О чём поговорить.** «В чём разница между origin и upstream в нашем процессе?» и «зачем

### Памятка преподавателю

- Это разговор, а не экзамен на зубрёжку — ведём беседу, при заминке подсказываем.
- Достаточно, чтобы студент объяснил **идею своими словами** и **зачем оно нужно**.
- 5–10 минут на человека: реально 1 основная тема + пара уточняющих вопросов.
